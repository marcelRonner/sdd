Management briefing

From spec-driven to intent-driven development

Why SDD repeats the problem of upfront design specs, and what owning the intent changes.

Based on K. V. Ahuja, "The Method That Replaces Spec-Driven Development — IDSD" (May 2026) and U. Barbini, "Spec-Driven Development: The New Waterfall" (August 2026)

This deck summarizes two authors' arguments. The framework overview on the last slide is from separate research, as of October 2026.

The problem with spec-driven development

One document, four jobs

The spec has to be intent, definition of done, workflow and technical context at once, written however the author felt that day.

A complete spec cannot be written up front

OpenAI's Symphony spec (2,169 lines) was distilled from a system that already ran. It was written last, not first.

The agent fills every hole

Gaps become agent decisions, at volume. Teams feel fast while being wrong; a 2025 METR trial found developers slower with AI but sure they were faster.

The cost does not disappear. Rework and wasted tokens move down the line to the client's invoice.

Source: Ahuja (May 2026). His own example: three days of rework, about $985 in tokens, from one good spec left unattended.

Key point: the holes are not a tooling defect. They come from asking people to specify everything before it exists.

The spec becomes the system

A spec precise enough to generate a system is as complex as the system. A vague one makes the agent guess, and drift starts early.

Regenerating is rewriting

The same spec yields different systems. Fixes made since the last run are lost, so teams edit code and the spec quietly goes stale.

Document churning

Agents produce plan after plan that reads well but was never tested against reality. Only running code has to match reality.

Where agents do pay off: instant knowledge (APIs, legacy code) and cheap spikes that can be thrown away.

Source: U. Barbini, "Spec-Driven Development: The New Waterfall", Medium, August 2026.

Barbini concedes the tools are new and powerful, and that some SDD work is honest practice. His objection to regeneration rests on today's non-determinism and cost, which he expects to fall. He also promotes his own book, Process Over Magic. His "holodeck" image: an agent will specify something impossible without noticing, and heavily mocked tests can be green while connected to nothing.

The argument for intent: split the spec, assign owners

Human owns

Intent

The outcome wanted, with no technology in it. Five parts: description, constraints, failure scenarios, success scenarios, links to other intents.

Human owns

Expectations

The boundary: when the result counts as done, when it has failed, and the limits it must stay inside, in the user's terms.

Harness owns

Context

The how: tech stack, existing system, codebase constraints. Pulled in progressively by the tooling, not dumped into one document.

The agent builds and validates in a loop, but never decides what "done" means. People stay present in the loop instead of approving a large diff at the end.

Source: Ahuja's ICE frame (Intent, Context, Expectations), the basis of intent-driven software development (IDSD).

Practical first step from the article: take one real outcome this week, write the five parts of its intent, and ask an outsider where an agent would still have to guess. The author admits teams are not yet ready for this and that he has not fully solved staying in the loop.

Two critiques of SDD, one direction

Ahuja: intent-driven (IDSD)Barbini: keep it agile
DiagnosisOne spec does four jobs; every gap becomes an agent decisionSDD repeats CASE and MDA; a full spec is as complex as the code
Replaces the big specIntent and expectations, written by the outcome ownerExecutable, non-mocked tests; short docs checked against them
FrameworksHarnesses, not methodsScaffolding to learn from, not the destination
Way of workingAgent loops until expectations are metShort loops, riskiest part first, replan as you learn
Human roleOwns intent and the definition of done, stays in the loopDecides what the system should do and whether it is good enough

Combined: owners write intent and expectations; expectations become executable tests that stay the source of truth.

Sources: Ahuja (May 2026), Barbini (August 2026). The combined line is our synthesis, not either author's claim.

Both authors agree that documents alone do not hold, that frameworks are not the method, and that a person must own what "right" means. They differ on the artifact: Ahuja keeps owned markdown files (intent, expectations); Barbini wants tests as the spec, close to Gojko Adzic's specification by example. The two fit together: the expectations table in our IDSD example is already a set of examples that can be turned into tests. Barbini's caveat: tests only count if they touch the real system, and agents tend to over-mock.

Three processes compared

Upfront design spec

Classic, document-driven

Full spec by humans

Sign-off

Humans build

Test at the end

Breaks: a "complete" spec is an illusion; gaps surface late, change is slow and costly.

SDD

Spec-driven, with agents

One spec: what + how

Plan and tasks

Agent builds, fills gaps

Human reviews diff

Breaks: same upfront illusion, but now the gaps are filled instantly and at volume. The diff is too large to truly review.

IDSD

Intent-driven, with agents

Intent + expectations

Harness pulls context

Code, validate, repeat

Merge when met

Changes: one outcome at a time, done is defined by its owner, the loop repeats until expectations are met. Needs people present throughout.

Classic critique: Larman and Basili (IEEE Computer, 2003); Ostroff et al. (XP 2004). IDSD flow: Ahuja (May 2026).

SDD and classic upfront specs share one assumption: that someone can specify everything before it exists. The difference is speed. With agents, a gap is no longer a question to a colleague but an immediate, silent decision. IDSD's open risk, by the author's own account: it demands more discipline than most teams have today.

Spec Kit in detail: GitHub's open-source SDD toolkit

Constitution
Project rules every spec inherits

Specify
What to build and why

Clarify
Agent asks about gaps

Plan
Technical design and stack

Tasks
Ordered work items

Implement
Agent writes the code

What it is

  • Released by GitHub in September 2025, MIT licence, free
  • A CLI that installs templates and slash commands into the repository
  • Works with 30+ coding agents; no lock-in to one vendor
  • Most adopted SDD framework; best for greenfield work

Where it falls short

  • Specs do not update during implementation, so they drift from the code
  • Clarify and analyse steps are advisory; nothing gates the build
  • No check that the running code does what the spec says
  • Heavy ceremony for small changes and existing codebases

As of mid-2026. Sources: github.com/github/spec-kit, codemyspec.com, braingrid.ai, webreactiva.com. GitHub itself calls Spec Kit an experiment.

Link to the main argument: Spec Kit structures the workflow well, but spec, plan and context are still written up front and the human returns at review. That is the harness-without-method pattern the article criticises. Adoption figures differ by source (roughly 90k to 115k GitHub stars in the first half of 2026).

What a complete Spec Kit spec contains

spec.md: the chapters of the feature specification

1. User scenarios and testing (mandatory)Prioritised user stories (P1 to P3), each with an independent test and Given/When/Then acceptance scenarios
2. Edge casesBoundary conditions and error scenarios
3. Functional requirements (mandatory)Numbered requirements (FR-001 ...); unclear points flagged for clarification
4. Key entities (if data is involved)Data objects, their meaning and relationships
5. Success criteria (mandatory)Measurable, technology-agnostic outcomes (SC-001 ...)
6. AssumptionsDefaults, scope boundaries, dependencies on existing systems

Source: spec-template.md and plan-template.md in github.com/github/spec-kit (main branch, October 2026).

The spec itself deliberately holds the what and why; the how sits in plan.md and its companion files. Still, one feature produces up to eight documents written before any code exists, which is the upfront burden the article questions. Chapters 1, 3 and 5 map loosely to the article's intent and expectations; plan.md and the rest map to context. The one-line descriptions of research.md, data-model.md, contracts and quickstart.md are summaries, not template wording.

Walk through one hole: spec.md flags "does burgundy count as red?" and research.md answers it as an engineering decision. In the intent, the product owner answers it as constraint 1. Same answer, different owner. That is the core of the argument.
